  - Zero flights. Zero transport exposed in UI.

and `NtaDashboardPage.jsx`) was updated to consume the authenticated session from
`useAuth()` rather than falling back to hardcoded Jaipur dummy data.

3. MOCK VERSUS LIVE DATA FLOWS
------------------------------
A. Manage Plans Flow:
   - In Mock Mode (`isPlansMockMode()` true):
     - `getPlans`: Reads from `localMockStore` (initialized from `Database/seeds/plans.json`).
       For NTA, filters strictly by `plan.destination.toLowerCase() === session.region.toLowerCase()`.
     - `createPlan`: Prepends created plan to `localMockStore`. Overrides destination
       with `session.region` if user is NTA.
     - `updatePlan`: Updates in-memory record. Forbids cross-region editing or changing
       destination outside NTA region (403 Forbidden).
     - `deletePlan`: Strictly forbids NTA deletion (403 Forbidden). Only SuperAdmin can delete.
   - In Live Backend Mode (`isPlansMockMode()` false):
     - Calls `GET /plans`, `POST /plans`, `PATCH /plans/:id`, `DELETE /plans/:id` with
       identity headers (`x-user-role`, `x-user-id`, `Authorization: Bearer <token>`).
     - Backend `PlansService` enforces identical regional isolation checks.

B. Guide Applications Flow:
   - In Mock Mode (`isNtaMockMode()` true):
     - `getGuideApplications`: Filters `ntaMockStore.applications` by verifying the
       package belongs to the active NTA region (`regionalPlanMap`).
       With the new plans in `plans.json`, Goa, Delhi, Mumbai, Kerala, and Jaipur
       applications are properly matched and visible to their respective regional NTAs.
     - `updateGuideApplicationStatus`: Updates status ('accepted' | 'rejected') and
       persists `decisionNotes` and `decidedAt` in the in-memory store.
     - Limitations: Changes persist across tab navigation and re-renders within the session.
       A full browser refresh resets in-memory mock store back to initial fixtures.
   - In Live Backend Mode (`isNtaMockMode()` false):
     - Calls `GET /guide-requests` and `PATCH /guide-requests/:id`.
     - Limitations: The backend `GuideRequest` entity only stores `status` and `guideId`.
       Rejection notes are not persisted to the backend database.
