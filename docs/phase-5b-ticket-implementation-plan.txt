4. EXISTING BACKEND & API CONTRACTS
--------------------------------------------------------------------------------
Backend API (untouched per constraints):
- `POST /tickets`:
  - Request body: `{ subject, message, category?, priority? }`
  - Headers: `Authorization: Bearer <token>`
  - Permitted Roles: `TRAVELLER`, `GUIDE`, `HOTEL`, `EXPERIENCE`
- `GET /tickets`:
  - Returns caller's own tickets for ordinary submitters; returns all tickets for `TECHADMIN`.
- `PATCH /tickets/:id`:
  - Request body: `{ resolution? }` (max 800 chars)
  - Permitted Role: `TECHADMIN` only.

API Service (`frontend/src/services/tickets.api.js`):
- `createTicket(data)`
- `getTickets()`
- `resolveTicket(ticketId, resolution)`

6. SUBMITTER ROLE INFERENCE CONTRACT
--------------------------------------------------------------------------------
Since the backend schema stores submitter in `ticket.travellerId` / `ticket.travellerName`:
- IDs starting with `HP` or containing `hotel` -> "Hotel Partner" badge.
- IDs starting with `G` or containing `guide` -> "Guide" badge.
- IDs starting with `XP` or containing `experience` -> "Experience Partner" badge.
- IDs starting with `T`, `20001`, or default -> "Traveler" badge.
If a submitter's human-readable name or explicit role field is added to the backend in the future,
the UI will seamlessly prioritize `ticket.submitterRole` or `ticket.submitterName` without breaking.
