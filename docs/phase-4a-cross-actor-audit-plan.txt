--------------------------------------------------------------------------------
1. OBJECTIVE & SCOPE
--------------------------------------------------------------------------------
The objective of Phase 4A is to conduct an exhaustive, non-destructive audit of the Xploreo codebase (frontend and backend) to determine whether data access, CRUD operations, authentication, session propagation, and authorization work correctly across all seven defined platform actors:
1. SuperAdmin (SA)
2. Non-Tech Admin (NTA)
3. Tech Admin (TA)
4. Traveler
5. Hotel Partner
6. Guide
7. Experience Partner

This audit strictly inspects:
- Unauthorized cross-actor data access (IDOR / vertical & horizontal privilege escalation).
- Missing, incomplete, or bypassed backend authorization.
- Record ownership verification vs client-supplied identifiers.
- Regional isolation and scoping (specifically for Non-Tech Admin and Hotel/Guide resources).
- Inconsistent frontend permission checks vs backend guard enforcement.
- Mock data and client-side fallback stores operating in lieu of or alongside real backend APIs.
- Incomplete schemas, missing validation DTOs, and payment/financial mock seams.

PROTECTED CONSTRAINTS:
- AUDIT ONLY: No application code, test suites, controllers, guards, DTOs, entities, seed data, routes, configs, or package dependencies will be modified.
- No browsers or live servers will be launched.
- No destructive requests or operations will be executed against shared or production data.

3. VERIFICATION METHODOLOGY & CONFIDENCE TAXONOMY
--------------------------------------------------------------------------------
To ensure absolute fidelity and avoid unsubstantiated claims, every finding and CRUD matrix cell is categorized using four strict confidence levels:

1. CONFIRMED BY SOURCE:
   The actual source code explicitly and unambiguously establishes the behavior (e.g., presence or absence of `@Roles()`, manual check of `req.user.userId === resource.userId`, query filtering by `region`, or in-memory mock store override).
2. VERIFIED BY EXECUTION:
   A non-destructive automated test or CLI test runner was executed directly and demonstrated the behavior.
3. INFERRED:
   The architectural pattern or surrounding code suggests the behavior, but it cannot be definitively proven without runtime test execution.
4. UNVERIFIED:
   Evidence is insufficient or conflicting across modules, requiring explicit verification or developer clarification.

4. RULE-BY-RULE VERIFICATION STRATEGY
--------------------------------------------------------------------------------

A. Authentication & Session Propagation:
   - Verification: Check `AuthGuard` in `backend/src/common/guards/auth.guard.ts` vs `frontend/src/services/session.js`.
   - Goal: Determine how tokens/headers are verified, whether `x-user-role` and `x-user-id` can be spoofed, and whether JWTs/signatures are used.

B. Actor Role Enforcement (RBAC):
   - Verification: Compare `@Roles(...)` decorators on every controller route against the permitted matrix.
   - Goal: Check if endpoints are accessible without `@Roles()` (inheriting only class-level `@Roles()` or defaulting to any authenticated role).

C. Horizontal IDOR & Record Ownership Isolation:
   - Verification: In every mutate/read endpoint (`/trips/:id`, `/bookings/:id`, `/hotels/:id`, `/tickets/:id`, `/reviews/:id`), check whether `req.user.userId` is compared against the resource owner, or whether caller-supplied IDs in URL parameters or request bodies are trusted.

D. Non-Tech Admin Regional Isolation:
   - Verification: Inspect `PlansController.findAll`, `create`, `update`, `remove` and `TripsController.findAll`, plus `guide-requests`.
   - Goal: Check if the backend queries filter by the NTA's assigned region (or `x-user-location`), or if filtering is purely frontend-side. Check if an NTA can mutate packages in other regions by passing arbitrary IDs.

E. Financial & Payout Operations:
   - Verification: Inspect `superadmin.api.js`, `paymentService.js`, and backend controllers.
   - Goal: Confirm which financial endpoints (payouts, refunds, disputes, ledger) exist in the NestJS backend vs frontend mock-only implementations.

F. Mock vs Live Inconsistencies:
   - Verification: Inspect `isSuperAdminMockMode()`, `isNtaMockMode()`, `isPlansMockMode()`, and `paymentService.js`.
   - Goal: Document where client mock stores hide missing backend endpoints or mask backend failures.
