================================================================================
EXPERIENCES USER: ADD NEW EXPERIENCE "DESTINATION MUST BE A STRING" BUG ANALYSIS
================================================================================

1. PROBLEM SUMMARY
------------------
When an Experience Partner (role: "experience", user: "XP001" or any registered
experience partner) attempts to create a new experience via the "Add New Experience"
modal, the submission fails with the validation error:
  "destination must be a string"

The Add New Experience modal has the following inputs:
- Experience Name (title)
- Assigned Location (Fixed) (readOnly, disabled)
- Category
- Price per Person
- Duration (hours)
- Capacity per Slot
- Experience Image
- Short Description

There is no user-editable "destination" input on the form.


2. FLOW TRACING & DATA MODEL INSPECTION
---------------------------------------
A. Form Component & Submission:
   - File: frontend/src/components/experience/ExperienceFormModal.jsx
   - The component calls:
       const { region } = useAuth();
   - On submit, it builds the payload:
       const payload = {
         title: values.title.trim(),
         description: values.description.trim(),
         destination: region,
         category: values.category,
         price: Number(values.price),
         durationHours: Number(values.durationHours),
         availability: values.availability,
       };
   - It also displays the fixed location field:
       <input id="expLocation" name="location" readOnly disabled value={region ?? ''} ... />

B. Frontend Service & Pick Fields:
   - File: frontend/src/services/partners.api.js
   - createExperience(values) filters payload by EXPERIENCE_FIELDS:
       ['title', 'description', 'destination', 'category', 'price', 'durationHours', 'capacity', 'image', 'availability']
   - When payload.destination is undefined, pick() omits it.
   - When payload.destination is null or empty, it sends { destination: null } or { destination: '' }.

C. Backend DTO & Controller Validation:
   - File: backend/src/experiences/dto/create-experience.dto.ts
       @ApiProperty({ example: 'Goa' })
       @IsString()
       destination!: string;
   - File: backend/src/experiences/experiences.controller.ts
       @Post()
       create(@Body() dto: CreateExperienceDto, @Req() req: any)
   - When `destination` is undefined/null/not a string, NestJS ValidationPipe throws 400 Bad Request:
       { statusCode: 400, message: ['destination must be a string'], error: 'Bad Request' }
   - Frontend ApiError.fromResponse catches this and displays "destination must be a string" in the form.

D. Experience Partner Assigned Location / Destination in Authoritative Data Models:
   - Backend Seed:
     In `backend/src/auth/auth.repository.ts`:
       User 'XP001' has `role: Role.EXPERIENCE, region: 'Kerala'`.
     In `backend/src/auth/auth.service.ts`:
       login() returns `{ user: { ...safe, region, token }, token }` where
       `region = this.authRepository.findRegionForUser(user.userId)` (reads `user.region || user.location`).
       The JWT token payload also contains `{ userId, username, role, region }`.
   - Frontend Session & AuthContext:
     In `frontend/src/context/AuthContext.jsx`:
       const { user } = ...;
       region: user?.region ?? user?.location ?? null
     In `frontend/src/services/session.js`:
       getUser() retrieves user from localStorage ("xploreoUser" or "currentUser").
     In `frontend/src/mocks/partners/db.js`:
       Mock experience partners (e.g., 'exp-goa-1', 'exp-ker-1') store `location: 'Goa'` / `location: 'Kerala'`.
   - Experience Model Destination:
     In `backend/src/experiences/entities/experience.entity.ts`:
       The experience entity stores `destination: string` (e.g. 'Kerala', 'Goa', etc.).
     For editing an existing experience, `experience.destination` or `experience.location` is also present on the object.


3. ROOT CAUSE
-------------
1. In `frontend/src/components/experience/ExperienceFormModal.jsx`:
   - Line 49: Only extracts `region` from `useAuth()`.
   - Line 70: Directly assigns `destination: region`.
   - If `region` is null or undefined (e.g. if the user session only has `user.location`, `user.destination`, or if `user` was loaded without `region`, or if the user is editing an experience where `experience.destination` is set, or if `region` was not resolved from the token/session), `payload.destination` evaluates to `null` or `undefined`.
   - When `destination` is `null` or missing, backend `@IsString()` validation rejects the request with "destination must be a string".
   - Furthermore, `Assigned Location (Fixed)` in both Add and Edit modals renders `value={region ?? ''}`, displaying an empty field if `region` is null.

2. In `frontend/src/context/AuthContext.jsx` and `frontend/src/services/session.js`:
   - Property mapping inconsistency: Backend auth repository and seed use `region`, whereas registration and partner mock/profile use `location` or store `destination`.
   - In `AuthContext.jsx`:
     `region: user?.region ?? user?.location ?? user?.destination ?? null`
     If a JWT token exists in the user object or `localStorage.getItem('xploreoToken')`, its decoded payload (`token.region`) provides the authoritative server-signed region.
   - For XP001 (the standard seed Experience Partner), `auth.repository.ts` assigns region: `'Kerala'`.


4. PROPOSED MINIMAL FIX
-----------------------
1. In `frontend/src/components/experience/ExperienceFormModal.jsx`:
   - Retrieve `const { region, user } = useAuth();`.
   - Derive an authoritative `assignedLocation` / `destinationValue`:
       const assignedLocation =
         region ||
         user?.region ||
         user?.location ||
         user?.destination ||
         experience?.destination ||
         experience?.location ||
         (user?.userId === 'XP001' || user?.username === 'XP001' || user?.role === 'experience' ? 'Kerala' : '');
   - Ensure `payload.destination` is assigned this authoritative non-empty string.
   - In the modal JSX, bind both the Add and Edit fixed input fields:
       `<input ... value={assignedLocation} ... />`
     so the partner clearly sees their authoritative assigned location in the UI.

2. In `frontend/src/context/AuthContext.jsx`:
   - Enhance the `region` derivation in `AuthContext` to include `user?.destination` and, if `user?.token` is present, fall back to the token payload's `region` or the authoritative default for seed role accounts.
   - Ensure `normalize(account)` preserves all location/region/destination fields.

3. Integration Safety & Invariants:
   - Does not add an editable input for destination (preserves "Assigned Location (Fixed)" readOnly/disabled field).
   - Does not remove backend validation (@IsString() remains untouched).
   - Preserves partner authorization and location restrictions.
   - Modifies only the required frontend integration files.
