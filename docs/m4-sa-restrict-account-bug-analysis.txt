================================================================================
XPLOREO M4 BUG ANALYSIS: SUPERADMIN RESTRICT ACCOUNT HTTP 400
Document: docs/m4-sa-restrict-account-bug-analysis.txt
Status: COMPLETED ROOT CAUSE INVESTIGATION
================================================================================

1. PROBLEM SUMMARY
--------------------------------------------------------------------------------
On the SuperAdmin -> Users & Partner Management page (`frontend/src/pages/SuperAdmin/users.jsx`),
clicking "Yes, Restrict Account" in the confirmation modal fails with:
`HTTP error! status: 400`

2. EXECUTION ENVIRONMENT & ACTIVE DATA FLOW
--------------------------------------------------------------------------------
1. Running Mode:
   - SuperAdmin mock mode (`isSuperAdminMockMode()`) is FALSE because `VITE_MOCKS`
     is not set to 'superadmin' or 'all'.
   - The frontend issues real network calls to the live NestJS backend at
     `http://localhost:3000/api`.

2. The Request Produced by the Action:
   - User action: In `users.jsx`, `handleConfirmStatusChange()` triggers:
     `updateUserStatus(targetUser.userId || targetUser.username, nextStatus, session)`
     where `nextStatus` is `'inactive'` (or `'active'` for reactivate).
   - API call: `updateUserStatus()` in `frontend/src/services/superadmin.api.js`:
     * Target URL: `PATCH http://localhost:3000/api/auth/users/:userId`
     * Headers: `{ 'x-user-role': 'superadmin', 'x-user-id': 'SA001', 'Content-Type': 'application/json', Authorization: 'Bearer <token>' }`
     * Request Body: `{"status": "inactive"}` (or `{"status": "active"}`)

3. EXACT BACKEND REJECTION & ROOT CAUSE IDENTIFICATION
--------------------------------------------------------------------------------
1. Global Validation Pipe Enforcement:
   - In `backend/src/main.ts`:
     ```ts
     app.useGlobalPipes(
       new ValidationPipe({
         whitelist: true,
         forbidNonWhitelisted: true,
         transform: true,
       }),
     );
     ```
     With `forbidNonWhitelisted: true`, any incoming property not decorated with a
     validation decorator in the endpoint's DTO triggers an HTTP 400 Bad Request exception.

2. DTO Definition Mismatch:
   - Endpoint: `PATCH /api/auth/users/:id` in `backend/src/auth/auth.controller.ts`
     accepts `@Body() dto: UpdateAuthDto`.
   - `UpdateAuthDto` in `backend/src/auth/dto/update-auth.dto.ts`:
     ```ts
     export class UpdateAuthDto extends PartialType(RegisterDto) {}
     ```
   - `RegisterDto` in `backend/src/auth/dto/create-auth.dto.ts` only defines:
     `username`, `password`, `name`, `email`, `phone`, `role`, `location`.
   - `status` is NOT defined on `RegisterDto` or `UpdateAuthDto`.

3. Actual Backend Response:
   ```json
   {
     "success": false,
     "statusCode": 400,
     "path": "/api/auth/users/T001",
     "method": "PATCH",
     "message": ["property status should not exist"]
   }
   ```
   Because `status` is not a whitelisted property in `UpdateAuthDto`, NestJS's
   ValidationPipe immediately rejects the request with HTTP 400: `property status should not exist`.

4. Secondary Observation (Authorization & Login Enforcement):
   - In `backend/src/auth/auth.service.ts`:
     * `update(id, dto, actor)` allows SuperAdmin to update any account:
       ```ts
       const isAdmin = actor?.role === 'superadmin';
       if (!isAdmin) {
         if (actor?.userId !== id) throw new ForbiddenException(...);
         if (dto.role !== undefined) throw new ForbiddenException(...);
       }
       ```
     * Only SuperAdmin should be permitted to mutate an account's `status`. Non-admin
       users must not be able to change their own or others' status.
     * In `login(dto)`: Currently, login does not check `user.status`. If an account is
       restricted (`status === 'inactive'`), login should fail with an appropriate
       message, or at minimum, the restriction status must be faithfully persisted and
       reflected across all administrative reads and listings.
   - In `frontend/src/services/superadmin.api.js`:
     * `buildAdminHeaders(session)` only attached `x-user-role` and `x-user-id`.
       Now that backend requires signed Bearer tokens (`AuthGuard`), `fetchData()` in `api.js`
       merges `identityHeaders()` so `Authorization: Bearer <token>` is present, but
       `buildAdminHeaders()` should also explicitly ensure `identityHeaders()` or the session token
       is honored.
     * `fetchData()` in `frontend/src/services/api.js` currently throws a generic
       `HTTP error! status: 400` when response is not ok, without extracting `payload.message`.

4. MINIMAL CORRECT FIX STRATEGY
--------------------------------------------------------------------------------
1. Backend DTO (`backend/src/auth/dto/update-auth.dto.ts`):
   - Add `@ApiPropertyOptional()` and `@IsOptional()` `@IsIn(['active', 'inactive'])`
     for `status?: 'active' | 'inactive';`.
2. Backend Authorization Guard in `AuthService.update()`:
   - Ensure `dto.status !== undefined` is restricted to SuperAdmin (or authorized admin).
     If a non-admin attempts to pass `status`, reject with `ForbiddenException('Only administrators can change account status.')`.
3. Backend Login Enforcement in `AuthService.login()`:
   - Check if `user.status === 'inactive'`.
   - Throw `UnauthorizedException('Account is restricted. Please contact support.')`.
4. Backend Repository Persistence (`backend/src/auth/auth.repository.ts`):
   - `update(userId, data)` already calls `this.users[idx] = { ...this.users[idx], ...stripUndefined(data) }`,
     so `status` will update in memory and persist across all queries.
5. Frontend Error Reporting in `fetchData` / `superadmin.api.js`:
   - Parse error messages from response JSON so descriptive validation messages are surfaced
     rather than a bare `HTTP error! status: 400`.
6. Rebuild and Verify:
   - Rebuild backend (`nest build`) and restart process.
   - Run backend tests and verify status updates via API.
