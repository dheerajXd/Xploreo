XPLOREO M4 BUG FIX REPORT: SUPERADMIN RESTRICT ACCOUNT HTTP 400

================================================================================

1. ISSUE SUMMARY
--------------------------------------------------------------------------------
On the SuperAdmin -> Users & Partner Management page (`frontend/src/pages/SuperAdmin/users.jsx`),
clicking "Yes, Restrict Account" in the confirmation modal resulted in:
`HTTP error! status: 400`

2. ROOT CAUSE
--------------------------------------------------------------------------------
1. Global Validation Pipe Enforcement:
   - In `backend/src/main.ts`, the application registers NestJS's `ValidationPipe` with
     `whitelist: true` and `forbidNonWhitelisted: true`.
   - Any property present in an incoming request body that lacks class-validator decorators
     in the target endpoint's DTO triggers an immediate `BadRequestException` (HTTP 400).
2. Missing DTO Property:
   - The restriction handler calls `PATCH /api/auth/users/:id` with payload `{"status": "inactive"}`.
   - The endpoint accepted `@Body() dto: UpdateAuthDto`.
   - `UpdateAuthDto` in `backend/src/auth/dto/update-auth.dto.ts` extended `PartialType(RegisterDto)`.
   - Neither `RegisterDto` nor `UpdateAuthDto` declared the `status` field.
   - Consequently, the ValidationPipe rejected the payload with:
     `{"statusCode": 400, "message": ["property status should not exist"]}`.
3. Frontend Generic Error Reporting:
   - `fetchData()` in `frontend/src/services/api.js` threw `new Error("HTTP error! status: " + response.status)`
     without parsing `payload.message`, masking the underlying validation error.

3. CHANGES IMPLEMENTED
--------------------------------------------------------------------------------
1. `backend/src/auth/dto/update-auth.dto.ts`:
   - Added optional validated `status` property to `UpdateAuthDto`:
     ```ts
     @ApiPropertyOptional({ enum: ['active', 'inactive'], example: 'inactive' })
     @IsOptional()
     @IsString()
     @IsIn(['active', 'inactive'])
     status?: 'active' | 'inactive';
     ```
2. `backend/src/auth/auth.service.ts`:
   - Restricted status modification strictly to administrators in `update()`:
     ```ts
     if (dto.status !== undefined) {
       throw new ForbiddenException('Only administrators can change account status.');
     }
     ```
   - Enforced restriction on authentication in `login()`:
     ```ts
     if (user.status === 'inactive') {
       throw new UnauthorizedException('Account has been restricted. Please contact support.');
     }
     ```
3. `frontend/src/services/api.js`:
   - Updated `fetchData()` error handling to inspect and extract `payload.message`
     when an API request fails, surfacing meaningful error descriptions.

4. VERIFICATION RESULTS
--------------------------------------------------------------------------------
1. Restrict Account via SuperAdmin Token:
   - Request: `PATCH /api/auth/users/G001` with `{"status": "inactive"}`
   - Result: `HTTP 200 OK`
   - Response Payload: `status: "inactive"` persisted correctly.
2. Login Attempt by Restricted User:
   - Request: `POST /api/auth/login` for `G001`
   - Result: `HTTP 401 Unauthorized`
   - Message: `"Account has been restricted. Please contact support."`
3. Reactivate Account via SuperAdmin Token:
   - Request: `PATCH /api/auth/users/G001` with `{"status": "active"}`
   - Result: `HTTP 200 OK`
   - Response Payload: `status: "active"` restored.
4. Login Attempt by Reactivated User:
   - Request: `POST /api/auth/login` for `G001`
   - Result: `HTTP 201 Created` with valid session token and `status: "active"`.
5. Non-Admin Security Check:
   - Request: `PATCH /api/auth/users/G001` with `status: "inactive"` using Guide token
   - Result: `HTTP 403 Forbidden` (`"Only administrators can change account status."`).
6. Build Validation:
   - Backend (`nest build`): Compiled cleanly with 0 errors.
   - Frontend (`vite build`): Production bundle compiled in 852ms with 0 errors.
