================================================================================
XPLOREO NTA MOCK DATA AUDIT REPORT
================================================================================

1. EXECUTIVE SUMMARY
-------------------
This audit provides a source-level investigation of the data origins, service
layers, regional filtering, and authorization controls for Non-Tech Admin (NTA)
Manage Plans and Guide Applications in Xploreo.

Key Findings:
1. Plans Data Coverage:
   - `Database/seeds/plans.json` only contains 3 records covering 2 regions:
     Kerala (plan-1) and Jaipur (plan-2, plan-jaipur-heritage-01).
   - Goa, Delhi, and Mumbai have 0 plans in `Database/seeds/plans.json`.
   - In contrast, the partner hotel catalog (`Database/fixtures/hotels/catalog.json`)
     and experience catalog (`Database/fixtures/experiences/catalog.json`) have
     established records for all 5 regions (Jaipur, Goa, Delhi, Mumbai, Kerala).

2. Guide Applications Data Coverage:
   - `Database/fixtures/admin/nta_metrics.json` defines 12 guide applications
     across Jaipur, Goa, Kerala, Delhi, and Mumbai with pending, accepted, and
     rejected statuses.
   - However, several applications reference packages that do not exist in
     `Database/seeds/plans.json` (e.g. `plan-goa-coastal-02`, `plan-delhi-monuments-04`,
     `plan-mumbai-harbour-05`, `plan-jaipur-crafts-06`).
   - Because `nta.api.js` (lines 414-422) cross-checks guide applications against
     `getMockPlansStore()`, applications for Goa, Delhi, and Mumbai are filtered out
     as orphaned unless matching packages exist in the plans store!

3. Authentication & Assigned-Region Resolution:
   - In `PlansPage.jsx` and `GuidesPage.jsx`, the components previously used:
       `const activeUser = currentUser || user || { userid: 'NTA-JAI-001', role: 'nontechadmin', region: 'Jaipur' };`
   - If accessed via the router `/nta/plans` or `/nta/guides` without props, they
     fell back to a hardcoded Jaipur user instead of consuming the authenticated
     user from `useAuth()`.
   - In `AuthContext.jsx`, `normalize(account)` now decodes JWT claims, but an
     explicit default region for NTA seed user `NTA001` ('Jaipur') should be
     guaranteed when session storage lacks an explicit region key.

4. Mock vs Live Backend Behaviors:
   - In `plans.api.js`:
     - Live calls go to `GET /plans`, `POST /plans`, `PATCH /plans/:id`, `DELETE /plans/:id`.
     - Mock mode operates on in-memory `localMockStore`.
     - In both modes, NTA region isolation is enforced: an NTA can only read, create,
       and update plans matching their assigned region. SuperAdmin can access all.
     - NTA delete attempts return a 403 Forbidden error (SuperAdmin-only privilege).
   - In `nta.api.js`:
     - Live calls go to `GET /guide-requests` and `PATCH /guide-requests/:id`.
     - Mock mode operates on `ntaMockStore.applications`.
     - In mock mode, decision notes and reasons are recorded in `ntaMockStore`.
     - In live backend mode, `GuideRequest` entity only stores `status` and `guideId`;
       rejection notes are not persisted to the backend database.

5. Test Execution Status:
   - Backend automated test suite executed:
     `npm test` in `backend/` -> 1 suite, 15 tests PASSED (including NTA regional
     isolation in `auth-security.spec.ts`).
   - Frontend components and mock services have no existing automated test runners;
     these were verified via source-code inspection and build compilation.


2. DETAILED AUDIT FINDINGS BY MODULE
-----------------------------------

### MODULE 1: NTA MANAGE PLANS

A. Files & Data Sources:
   - Canonical dataset: `Database/seeds/plans.json` imported via
     `frontend/src/mocks/plans/plans.fixture.js`.
   - UI Components:
     - `frontend/src/pages/NonTechAdmin/plans.jsx`
     - `frontend/src/components/nta/PlanList.jsx`
     - `frontend/src/components/nta/PlanForm.jsx`
   - Service: `frontend/src/services/plans.api.js`

B. Current Data Gaps:
   - Current records in `seeds/plans.json`:
     1. `plan-1` -> Kerala (5 nights, 22000 INR)
     2. `plan-2` -> Jaipur (7 nights, 35000 INR)
     3. `plan-jaipur-heritage-01` -> Jaipur (4 nights, 24500 INR)
   - Missing regions in plans fixture: Goa, Delhi, Mumbai.
   - Result: When an NTA assigned to Goa, Delhi, or Mumbai opens Manage Plans,
     the list is completely empty.

C. Regional Filtering & Tamper Resistance:
   - In `PlanList.jsx`:
     - If `assignedRegion` is present, the destination pill is locked to
       `assignedRegion` (disabled, cannot be clicked to switch regions).
     - Plans are strictly filtered: `plan.destination.toLowerCase() !== assignedRegion.toLowerCase()`
       are excluded.
     - For SuperAdmin (`!assignedRegion`), destination pills for 'All' and all 5 regions
       are selectable.
   - In `PlanForm.jsx`:
     - If `isRegionLocked` is true (NTA with assigned region), the Destination input
       is rendered as a read-only disabled text field displaying the assigned region.
     - SuperAdmin sees a dropdown selector to choose any of the 5 supported regions.
   - In `plans.api.js`:
     - `createPlan`: Forces `destination` to `session.region` if user is NTA:
         `const effectiveDestination = (isNTA && session.region ? session.region : data.destination || '').trim();`
       Client-supplied destination values in payload CANNOT override the authenticated NTA region.
     - `updatePlan`: Rejects with 403 if an NTA attempts to edit a plan outside their region
       or change a plan's destination to another region.
     - `deletePlan`: Returns 403 Forbidden for NTA; only SuperAdmin may delete plans.
   - In Backend `PlansService`:
     - `create`: Throws 403 Forbidden if NTA attempts to create outside `actor.region`.
     - `findAll`: Ignores query param `destination` for NTA and forces `effectiveDestination = actor.region`.
     - `findOne` & `update`: Enforces that the target plan destination matches `actor.region`.
     - `remove`: Only permitted for SuperAdmin.


### MODULE 2: NTA GUIDE APPLICATIONS

A. Files & Data Sources:
   - Canonical dataset: `Database/fixtures/admin/nta_metrics.json` imported via
     `frontend/src/mocks/nta/nta.fixture.js`.
   - UI Components:
     - `frontend/src/pages/NonTechAdmin/guides.jsx`
   - Service: `frontend/src/services/nta.api.js`

B. Current Data Gaps & Cross-Dataset Inconsistencies:
   - `nta_metrics.json` defines 12 guide applications:
     - Jaipur: `g-req-001` (pending), `g-req-005` (accepted), `g-req-010` (rejected)
     - Goa: `g-req-002` (pending), `g-req-011` (accepted), `g-req-008` (rejected)
     - Kerala: `g-req-003` (pending), `g-req-012` (accepted), `g-req-009` (rejected)
     - Delhi: `g-req-004` (pending), `g-req-006` (accepted), `g-req-013` (rejected)
     - Mumbai: `g-req-014` (pending), `g-req-007` (accepted), `g-req-015` (rejected)
   - Discrepancy: The Goa, Delhi, and Mumbai applications reference package IDs:
     - `plan-goa-coastal-02`
     - `plan-delhi-monuments-04`
     - `plan-mumbai-harbour-05`
     - `plan-jaipur-crafts-06`
     - `plan-kerala-backwaters-03`
     None of these packages exist in `Database/seeds/plans.json`!
   - Result: In `nta.api.js:414-422`, `getGuideApplications` filters out applications
     whose `packageId` is not present in `getMockPlansStore()`. Consequently, NTAs
     for Goa, Delhi, and Mumbai see 0 guide applications in mock mode!

C. Regional Filtering & Decision Workflow:
   - In `GuidesPage.jsx`:
     - `loadData` requests `getGuideApplications({ destination: assignedRegion }, session)`
       and `getPlans({ destination: assignedRegion }, session)`.
     - Status tabs (All, Pending Review, Accepted, Rejected) filter the regional applications.
     - Review modal allows viewing credentials, rating, languages, and certifications.
     - Decision workflow allows Accepting or Rejecting pending applications.
   - Persistence & Limitations:
     - In mock mode: Updates persist within `ntaMockStore.applications` in memory during
       the browser session. Re-reviewing or switching tabs maintains the updated status
       and decision notes. Reloading the browser tab resets the in-memory store.
     - In live backend mode: Live `PATCH /guide-requests/:id` updates `status` and `guideId`,
       but `decisionNotes` are NOT persisted to the backend `GuideRequest` entity.


3. AUTHENTICATION & IDENTITY AUDIT
----------------------------------
- Identity Headers:
  `identityHeaders()` in `frontend/src/services/session.js` attaches:
    `x-user-role`: user.role
    `x-user-id`: user.userId
    `x-user-location`: user.region || user.location
    `Authorization`: Bearer <jwt-token>
- User Resolution Gap in NTA Pages:
  In `PlansPage.jsx` and `GuidesPage.jsx`, lines 16-22 / 35-42 read `currentUser || user || fallback`.
  However, in `routes/nontechadmin.routes.jsx`:
    `<Route path="plans" element={<PlansPage />} />`
    `<Route path="guides" element={<GuidesPage />} />`
  No user prop was passed from the route element. While `NtaLayout` calls `useAuth()`,
  the page components did not read `useAuth()`, defaulting to fallback `NTA-JAI-001` (Jaipur).
  Fix needed: In `PlansPage.jsx` and `GuidesPage.jsx`, import and call `useAuth()` to
  resolve the signed-in user and assigned region directly, ensuring NTAs from other
  regions (e.g. Goa, Kerala, Delhi, Mumbai) are correctly recognized.
