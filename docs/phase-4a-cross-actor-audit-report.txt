1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This audit evaluated the end-to-end security, authentication, session propagation, and authorization model of the Xploreo platform across all seven registered actors:
1. SuperAdmin (SA)
2. Non-Tech Admin (NTA)
3. Tech Admin (TA)
4. Traveler
5. Hotel Partner
6. Guide
7. Experience Partner

Key High-Level Findings:
1. TRUST-ON-FIRST-HEADER AUTHENTICATION ARCHITECTURE:
   The backend relies entirely on unverified client-supplied HTTP headers (`x-user-role` and `x-user-id`). There are no signed JWT tokens, session cookies, or HMAC cryptographic signatures. Any client or attacker can supply `x-user-role: superadmin` and `x-user-id: SA001` to completely bypass role checks and impersonate any user on the platform.

2. NON-TECH ADMIN (NTA) REGIONAL SCOPING IS FRONTEND-ONLY:
   While the frontend UI filters packages, bookings, and applications to the NTA's assigned region, the backend `PlansController` (`GET /plans`, `PATCH /plans/:id`), `TripsController` (`GET /trips`), and `GuideRequestsController` (`GET /guide-requests`, `PATCH /guide-requests/:id`) do NOT enforce any regional scoping. An NTA with an assigned region of "Jaipur" can read, modify, and update packages, trips, and guide requests in Goa, Delhi, Mumbai, or Kerala by changing request parameters or invoking backend endpoints directly.

3. MOCK DATA MASQUERADING AS LIVE FUNCTIONALITY IN ADMIN PORTALS:
   Extensive administrative and operational modules are completely backed by in-memory mock stores in the frontend rather than backend APIs:
   - SuperAdmin: Financial KPI charts, transaction ledger, refund processing queue, partner payout approvals, and dispute resolutions are mock-only (`superadmin.api.js`). No backend controller or database table exists for payouts, ledger, refunds, or disputes.
   - Non-Tech Admin: Guide application rejection notes and decision reasons are stored solely in frontend RAM; the backend `GuideRequest` entity drops decision reasons.
   - Payments: Checkout payment verification (`paymentService.js`) uses a mock adapter that simulates payment success without creating backend payment transactions.

4. INCONSISTENT HORIZONTAL AUTHORIZATION (IDOR):
   - Strict horizontal ownership IS enforced in: `BookingsService` (`findOne`, `cancel`, `checkIn`, `checkOut`), `GuideAssignmentsController` (`findForGuide`), and `TicketsService` (`findForUser`).
   - Weak or absent ownership checks exist in: `TravellerController` (`findOne` is unauthenticated public to any authenticated role), `GuideController` (`findOne` is unauthenticated public), and `TripsController` (`findOne` has no actor ownership check—any traveler or partner can view another traveler's detailed trip itinerary, pickup address, flight numbers, and passenger details by guessing the trip ID).

Mock Only (Missing Backend Endpoints):

- Operations Ledger: `getLedgerTransactions` is 100% frontend mock store (`mockStore.ledger`).

ACTOR 2: NON-TECH ADMIN (NTA)
-----------------------------------------------------------------------------------------------------------------------------
Frontend Routes: `/non-tech-admin/dashboard`, `/non-tech-admin/packages`, `/non-tech-admin/guides`, `/non-tech-admin/trips`.
Intended Scope: Regionally scoped to assigned region (e.g., Jaipur, Goa).
Actual Backend Enforcement:
- Travel Plans:
  - Read: Allowed on `GET /plans`. Scope: GLOBAL. Backend does NOT filter by NTA's region!
  - Create: Allowed on `POST /plans`. Scope: GLOBAL. NTA can create a package for ANY destination.
  - Update: Allowed on `PATCH /plans/:id`. Scope: GLOBAL. NTA can edit any package in any region.
  - Delete: Denied (HTTP 403) by `@Roles(SUPERADMIN)` on `DELETE /plans/:id`. Confirmed server-side.
- Trips:
  - Read: Allowed on `GET /trips`. Scope: GLOBAL. Backend returns all trips across all regions.
  - Create: Allowed on `POST /trips`.
  - Update: Allowed on `PATCH /trips/:id` and `PATCH /trips/:id/tracking`.
  - Delete: Denied (HTTP 403) by `@Roles(SUPERADMIN)`.
- Guide Requests:
  - Read: Allowed on `GET /guide-requests`. Scope: GLOBAL. Backend returns all guide requests platform-wide.
  - Update: Allowed on `PATCH /guide-requests/:id`. Can accept/reject guide requests in any region.
  - Delete: Allowed on `DELETE /guide-requests/:id`.
- Guides & Travellers:
  - Read: Allowed on `GET /guide` and `GET /traveller`. Scope: GLOBAL.
  - Update: Allowed to update any guide or traveller profile (Service checks `actor?.role === 'nontechadmin'`).

  - Read: Allowed on `GET /tickets`. Filters by `travellerId === req.user.userId`.
- Reviews:
  - Create: Allowed on `POST /reviews`. Validates completed trip ownership. Confirmed server-side.

5. AUTHENTICATION AND API VALIDATION FINDINGS
--------------------------------------------------------------------------------

1. HEADER-BASED AUTHENTICATION WITHOUT CRYPTOGRAPHIC SIGNATURES:
   - Severity: CRITICAL
   - Location: `backend/src/common/guards/auth.guard.ts:23-44`
   - Details: `AuthGuard` extracts identity from `req.headers['x-user-role']` and `req.headers['x-user-id']`. It performs no validation of a cryptographic JWT, bearer token, or session cookie. Any HTTP client (cURL, Postman, script) can issue a request with `x-user-role: superadmin` and `x-user-id: SA001` and the backend will execute the action with full SuperAdmin privileges.

2. HORIZONTAL PRIVILEGE ESCALATION (IDOR) ON TRIP INSPECTION:
   - Severity: HIGH
   - Location: `backend/src/trips/trips.controller.ts:63-85`, `backend/src/trips/trips.service.ts:126-138`
   - Details:
     - `GET /trips/:id`: Controller has `@Roles(TRAVELLER, GUIDE, SUPERADMIN, NONTECHADMIN)`. In `TripsService.findOne(id)`, the trip is fetched and returned directly without verifying whether `trip.travellerId === req.user.userId` or `trip.guideId === req.user.userId`. Any traveler can read full itinerary, personal addresses, passenger counts, and pricing of any other traveler's trip.
     - `GET /trips/traveller/:travellerId`: Does not check if `:travellerId === req.user.userId`. Any authenticated traveler can enumerate all trips for any other traveler.

3. TRAVELLER AND GUIDE PROFILES ARE PUBLICLY ENUMERABLE:
   - Severity: MEDIUM
   - Location: `backend/src/traveller/traveller.controller.ts:49-54`, `backend/src/guide/guide.controller.ts:63-68`
   - Details: `GET /traveller/:id` and `GET /guide/:id` allow any authenticated actor (including other travelers or partners) to read the full profile, including email, phone number, and personal bio. While `PATCH` has self-ownership checks, `GET` has no ownership restrictions.

4. INCOMING PAYLOAD VALIDATION & EXTRA FIELD STRIPPING:
   - Location: `backend/src/main.ts:29-35`
   - Details: NestJS `ValidationPipe` is properly configured with `whitelist: true`, `forbidNonWhitelisted: true`, and `transform: true`. Unknown fields in request bodies are rejected with HTTP 400.

6. BACKEND-ENFORCED PERMISSIONS VS FRONTEND-ONLY RESTRICTIONS
--------------------------------------------------------------------------------

1. Non-Tech Admin Regional Restrictions are FRONTEND-ONLY:
   - In Frontend (`frontend/src/services/plans.api.js:126-130`, `frontend/src/components/nta/PlanList.jsx:47-66`):
     The client code checks `session.region` and sets `destination = session.region`, locking dropdowns and preventing the user from viewing other regions in the UI.
   - In Backend (`backend/src/plans/plans.controller.ts:59-79`, `backend/src/plans/plans.service.ts:41-55`):
     `GET /plans` takes optional query params (`page`, `limit`, `from`, `to`, `destination`). If an NTA calls `GET /plans?destination=Goa`, the backend returns Goa packages without checking the NTA's assigned region.
   - In Backend Mutations (`backend/src/plans/plans.controller.ts:88-98`, `backend/src/plans/plans.service.ts:63-67`):
     `PATCH /plans/:id` allows any user with role `NONTECHADMIN` to update any plan, regardless of the plan's destination. The backend service does not compare the plan's destination against the user's assigned region.

2. SuperAdmin Delete vs NonTechAdmin Delete:
   - Backend Enforced: `DELETE /plans/:id` is decorated with `@Roles(Role.SUPERADMIN)`. An NTA calling this endpoint receives HTTP 403 Forbidden. This is properly enforced on the backend.

3. Support Ticket Resolution:
   - Backend Enforced: `PATCH /tickets/:id` is decorated with `@Roles(Role.TECHADMIN)`. Ordinary actors receive HTTP 403 Forbidden from `RolesGuard`.

4. Hotel and Experience Booking Cancellation:
   - Backend Enforced: `PATCH /bookings/:id/cancel` and `PATCH /experience-bookings/:id/status` verify that the actor is either the traveler who booked it or the partner who owns the hotel/experience.

7. MOCK/LIVE DATA INCONSISTENCIES AND MISSING FUNCTIONALITY
--------------------------------------------------------------------------------

1. Financial Payouts & Commission Engine:
   - Frontend: `frontend/src/pages/SuperAdmin/finance.jsx` renders KPI cards, earnings breakdown charts, and a partner payout table with "Approve" and "Retry" action modals.
   - Reality: Calling `processPayoutAction` only updates an in-memory variable `mockStore.payouts` in `superadmin.api.js`. The backend NestJS app has zero financial endpoints, zero payout entities, and zero commission calculation tables.

2. Transaction Ledger, Refunds, & Dispute Management:
   - Frontend: `frontend/src/pages/SuperAdmin/opsbook.jsx` displays operational ledger tables, refund approval queues, and dispute resolution dialogs.
   - Reality: All functions (`getLedgerTransactions`, `processRefundAction`, `resolveDisputeAction`) mutate local variables in `superadmin.api.js`. No backend endpoints or database tables exist.

3. Checkout & Payment Gateway:
   - Frontend: `frontend/src/pages/Traveller/TravellerCheckoutPage.jsx` uses `paymentService.js`.
   - Reality: `mockPaymentAdapter` intercepts payment calls and produces simulated receipts (`RCPT-DEMO-XXXXXX`). If switched to `livePaymentAdapter`, it attempts to call `/payments/create-order` and `/payments/verify-payment`, which DO NOT EXIST in the backend and fail with 404.

4. NTA Guide Application Rejection Reasons:
   - Frontend: `frontend/src/services/nta.api.js` accepts a `reason` parameter when rejecting a guide application.
   - Reality: The backend `GuideRequest` entity and `PATCH /guide-requests/:id` only accept `{ status, guideId }`. The rejection reason is dropped on the floor and never stored on the server.

5. Silent Itinerary Transport Bridge:
   - Frontend: In `plans.api.js:77-87`, the frontend silently manufactures a dummy transport object (`Independent / Self-Arranged`, `status: planned`) because the backend `DayOneItinerary` entity requires non-null transport, even though Xploreo product specifications mandate "Hotel Stays + Curated Experiences ONLY (Zero flights, zero transport)".

8. FINDINGS PRIORITIZED BY SEVERITY
--------------------------------------------------------------------------------

[CRITICAL-01] Missing Cryptographic Authentication (Header-Spoofing Vulnerability)
- File: `backend/src/common/guards/auth.guard.ts:23-44`
- Impact: Complete platform compromise. Any external request can forge `x-user-role: superadmin` and `x-user-id: SA001` to gain unconstrained access to all admin routes.
- Required Fix: Implement JWT or session token issuance at login (`/auth/login`) and validate signature/expiration in `AuthGuard` rather than reading raw headers.

[CRITICAL-02] Missing Backend Regional Scoping for Non-Tech Admin
- Files: `backend/src/plans/plans.controller.ts:44-98`, `backend/src/plans/plans.service.ts:41-67`, `backend/src/trips/trips.controller.ts:55-61`
- Impact: Non-Tech Admins can view, edit, and create travel packages and trips in regions outside their jurisdiction simply by passing parameters or calling API endpoints directly.
- Required Fix: Look up the NTA's assigned region from the database (or verified session claim) in `PlansService` and `TripsService`, and restrict `findAll`, `create`, and `update` queries to matching `destination === nta.region`.

[HIGH-01] Horizontal Privilege Escalation (IDOR) on Trip Details
- Files: `backend/src/trips/trips.controller.ts:63-85`, `backend/src/trips/trips.service.ts:126-138`
- Impact: Any traveler can view full itinerary, booking amounts, and traveler identity of another traveler's trip by calling `GET /trips/:id` or `GET /trips/traveller/:travellerId`.
- Required Fix: Add an ownership check in `TripsService.findOne` ensuring caller is either `trip.travellerId`, `trip.guideId`, or an authorized admin. In `findByTraveller`, verify `travellerId === req.user.userId` unless caller is admin.
