1. EXECUTIVE SUMMARY & OBJECTIVE
--------------------------------------------------------------------------------
The Xploreo platform previously operated with a single regional Non-Tech Admin
(NTA) account: NTA001 (assigned to Jaipur). This project expands the NTA model
to 5 distinct regional accounts, each strictly scoped to one of the 5 official
supported regions:
  - NTA001: Jaipur
  - NTA002: Goa
  - NTA003: Delhi
  - NTA004: Mumbai
  - NTA005: Kerala

This expansion requires complete data consistency across both live backend
services and frontend mock/fixture modes, ensuring all actors (Traveler,
Hotel Partner, Experience Partner, Guide, SuperAdmin, TechAdmin, and NTA)
consume and mutate records from the same coherent data model without cross-region
leaks or orphaned foreign references.

2. COMPREHENSIVE REPOSITORY AUDIT (PHASE 1)
--------------------------------------------------------------------------------
2.1 Authentication & Regional Resolution:
  - Seed Accounts: `Database/seeds/users.json` only contains NTA001.
  - In-Memory Fallback: `backend/src/auth/auth.repository.ts` only seeds NTA001.
  - Username Lookup: In `auth.repository.ts:findByUsername()`, query 'nontechadmin'
    resolves to the first NTA user (NTA001). Explicit username queries (`NTA002`..
    `NTA005`) match `u.username.toLowerCase() === q`.
  - Region Resolution & JWT Signing: In `backend/src/auth/auth.service.ts`:
    `findRegionForUser(user.userId)` inspects `user.region || user.location`.
    The signed JWT payload contains `{ userId, username, role, region }`.
  - Frontend Session Restoration:
    * `frontend/src/context/AuthContext.jsx` normalizes user profiles.
      Currently contains a single fallback: `account.userId === 'NTA001' ? 'Jaipur' : undefined`.
      Must be updated to map `NTA001`->Jaipur, `NTA002`->Goa, `NTA003`->Delhi,
      `NTA004`->Mumbai, `NTA005`->Kerala, prioritizing trusted token claims.
    * `frontend/src/services/session.js` correctly clears `xploreoUser` and
      `currentUser` upon logout, preventing state bleed.

2.2 Regional Plans & Packages:
  - Repository Seed: `Database/seeds/plans.json` contains 10 verified plans:
    * PLAN-JPR-001, PLAN-JPR-002 -> Jaipur (NTA001)
    * PLAN-GOA-001, PLAN-GOA-002 -> Goa (NTA002)
    * PLAN-DEL-001, PLAN-DEL-002 -> Delhi (NTA003)
    * PLAN-BOM-001, PLAN-BOM-002 -> Mumbai (NTA004)
    * PLAN-KER-001, PLAN-KER-002 -> Kerala (NTA005)
  - Packages contain partner hotel stays and curated experiences only (no flights/transport).
  - Backend authorization in `PlansController` and `PlansService` enforces:
    * NTAs are constrained to their authenticated `req.user.region`.
    * Changing the payload `destination` cannot override the authenticated NTA's region.
    * Only SuperAdmin can create/mutate plans globally across all destinations.

2.3 Catalogs & Cross-Actor References:
  - Hotels: `Database/fixtures/hotels/catalog.json` contains verified hotel records
    for all 5 regions (HTL-JPR-01/02, HTL-GOA-01/02, HTL-DEL-01/02, HTL-BOM-01/02, HTL-KER-01/02).
  - Experiences: `Database/fixtures/experiences/catalog.json` contains verified
    experiences across all 5 regions (EXP-JPR-01/02, EXP-GOA-01/02, EXP-DEL-01/02, EXP-BOM-01/02, EXP-KER-01/02).
  - Plans in `Database/seeds/plans.json` match these exact hotel and experience IDs.

2.4 Guide Requests & Applications:
  - Backend Live Repository: `backend/src/guide-requests/guide-requests.repository.ts`
    pulls from `Database/seeds/guide_requests.json`. Currently has only 1 sample record (Kerala).
    Needs expansion to include guide requests for Jaipur, Goa, Delhi, Mumbai, and Kerala.
  - Frontend Fixtures: `Database/fixtures/admin/nta_metrics.json` contains
    `DEMO_GUIDE_APPLICATIONS` covering all 5 regions and matching plan IDs.
    Seeding backend `guide_requests.json` to mirror these records ensures 1:1 fidelity.

2.5 NTA Metrics & Dashboard Scoping:
  - `Database/fixtures/admin/nta_metrics.json` defines regional metrics:
    `regionalMetrics[Jaipur]`, `regionalMetrics[Goa]`, `regionalMetrics[Delhi]`,
    `regionalMetrics[Mumbai]`, `regionalMetrics[Kerala]`.
  - Frontend `nta.api.js` accurately computes dynamic metrics from the active
    scoped plans, applications, and bookings store per region.

3. ARCHITECTURE & SECURITY RULES (PHASE 2 & 3)
--------------------------------------------------------------------------------
1. Server-Side Trusted Region:
   - Client form inputs or query parameters cannot override `req.user.region`.
   - All plan creation/updates by NTA enforce `plan.destination = user.region`.
2. Regional Isolation:
   - NTA001 (Jaipur) cannot view or mutate Goa, Delhi, Mumbai, or Kerala records.
   - NTA002 (Goa) cannot view or mutate Jaipur, Delhi, Mumbai, or Kerala records.
   - Same constraint applies for NTA003, NTA004, and NTA005.
3. SuperAdmin Exemption:
   - SuperAdmin retains full global visibility and editing rights across all 5 regions.

4. STEP-BY-STEP IMPLEMENTATION PLAN

    Add NTA002 (Goa), NTA003 (Delhi), NTA004 (Mumbai), NTA005 (Kerala) with
    role 'nontechadmin', location/region appropriately set, password hash for 'NTA@123'.

  - Edit `frontend/src/context/AuthContext.jsx`:

    if not explicitly passed in payload.

Step 2: Region-Specific Live Data & Alignment (Phase 3 & 4)
  - Edit `Database/seeds/guide_requests.json`:
    Add guide application records for Jaipur, Goa, Delhi, Mumbai, Kerala
    corresponding to guides G001..G005 and matching valid plan IDs.
  - Verify hotel & experience references in plans match active partner catalogs.

Step 3: Automated Security & Regional Isolation Tests (Phase 6)
  - Add comprehensive test suites in `backend/src/auth/auth-security.spec.ts`:
    1. Authenticate NTA001 through NTA005; verify each resolves to its assigned region.
    2. Verify NTA001 token gets HTTP 403 / Forbidden on restricted Goa plan mutation.
    3. Verify NTA002 token gets HTTP 403 / Forbidden on restricted Jaipur plan mutation.
    4. Verify NTA003 (Delhi), NTA004 (Mumbai), NTA005 (Kerala) cross-region isolation.
    5. Verify NTA attempting to override destination in create DTO is forced to assigned region.
    6. Verify SuperAdmin can access and manage records across all regions.

Step 4: Build & Regression Validation
  - Run `npm test` in `backend/`.
  - Run `npm run build` in `backend/`.
  - Run `npm run build` in `frontend/`.
