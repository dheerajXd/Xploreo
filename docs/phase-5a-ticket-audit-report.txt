1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
The Xploreo support ticket workflow was audited across all five target actors:
- Ticket Submitters: Traveler, Hotel Partner, Guide, Experience Partner.
- Ticket Manager / Resolver: Tech Admin (TA).

Key Findings:
1. BACKEND FOUNDATION IS SOUND AND SECURE:
   - The backend `TicketsController`, `TicketsService`, and `TicketsRepository` are fully
     implemented, properly guarded with `@Roles()`, and seamlessly integrated with the
     Phase 4B signed JWT token authentication system.
   - Ownership is strictly derived from `req.user.userId`.
   - Role boundaries are enforced server-side: Ordinary actors can ONLY submit tickets and
     view their own tickets; Tech Admin can view ALL tickets across all submitters and is
     the ONLY actor permitted to resolve tickets.
   - Validation is enforced by `CreateTicketDto` (subject 3-140 chars, message 10-1200 chars,
     priority enum LOW/MEDIUM/HIGH, category max 80 chars) and `ResolveTicketDto` (resolution max 800 chars).

2. SUBMITTER PORTAL INTEGRATION STATUS:
   - Traveler (`/Traveller/tickets`): Fully implemented and routed. Uses `TicketCreateForm` and
     `TicketList`, integrated with `getTickets()` and `createTicket()`.
   - Guide (`/guide/support`): Fully implemented and routed. Uses `TicketCreateForm` and `TicketList`,
     integrated with backend API.
   - Experience Partner (`/experience/support`): Fully implemented and routed. Uses `TicketCreateForm`
     and `TicketList`, integrated with backend API.
   - Hotel Partner (`/hotel/support`): Route exists (`hotel.routes.jsx:29`) and points to
     `HotelSupport.jsx`, which wraps `TravellerSupportTicketsPage`. However, `HotelSupport` renders
     `TravellerSupportTicketsPage` with hardcoded fallback traveler defaults if `user` prop is not
     passed directly by the router layout!

3. TECH ADMIN QUEUE & RESOLUTION STATUS:
   - Tech Admin (`/tech-admin/tickets`): Fully implemented and routed in `techadmin.routes.jsx`.
   - Renders `TicketList` with `onResolveTicket={handleResolveTicket}`.
   - Successfully calls `getTickets()` (returning all tickets across all actors) and `resolveTicket()`.

4. IDENTIFIED WORKFLOW GAPS & REFINEMENTS:
   - In `backend/src/tickets/tickets.service.ts:24`, the field `travellerName` is stored as `userId`.
     While functional, it means tickets from hotel partners or guides display their `userId`
     (e.g., `HP001`, `G001`) instead of their human name or actor role in the Tech Admin queue.
   - In `backend/src/tickets/entities/ticket.entity.ts`, the field is named `travellerId` rather than
     a generic `submitterId` / `creatorId` (though it stores any actor's `userId`).
   - In-memory persistence: `TicketsRepository` stores tickets in an in-memory array (`private readonly tickets: Ticket[] = []`).
     While tickets survive frontend page refreshes during server runtime, tickets reset if the backend
     NestJS process restarts (consistent with all other repositories in this codebase).

3. DETAILED BACKEND AUDIT (SECURITY, OWNERSHIP & GUARDS)
--------------------------------------------------------------------------------

A. Role Guards & Endpoint Authorization:
- File: `backend/src/tickets/tickets.controller.ts`
  - `POST /tickets`:
    Decorated with `@Roles(Role.TRAVELLER, Role.GUIDE, Role.HOTEL, Role.EXPERIENCE)`.
    Tech Admin, Non-Tech Admin, and SuperAdmin cannot invoke `POST /tickets`.
    Enforced by `RolesGuard`. Confirmed by Source.
  - `GET /tickets`:
    Decorated with `@Roles(Role.TRAVELLER, Role.GUIDE, Role.HOTEL, Role.EXPERIENCE, Role.TECHADMIN)`.
    Enforced by `RolesGuard`. Confirmed by Source.
  - `PATCH /tickets/:id`:
    Decorated with `@Roles(Role.TECHADMIN)`.
    Only Tech Admin can invoke resolution. Submitting actors attempting to call `PATCH /tickets/:id`
    receive HTTP 403 Forbidden. Confirmed by Source.

B. Authenticated Identity Derivation:
- File: `backend/src/tickets/tickets.controller.ts:27`
  - In `create(@Body() dto: CreateTicketDto, @Req() req: any)`:
    Passes `req.user?.userId` to `ticketsService.create`.
    `req.user` is populated by `AuthGuard` from the cryptographically verified JWT token claims.
    Client-supplied headers or body fields cannot forge ticket ownership. Confirmed by Source.

C. Ownership Isolation & Horizontal IDOR:
- File: `backend/src/tickets/tickets.service.ts:32-36`
  - In `findForUser(userId: string | undefined, role: string | undefined)`:
    ```typescript
    if (role === Role.TECHADMIN) return this.ticketsRepository.findAll();
    if (!userId) throw new ForbiddenException('x-user-id header is required');
    return this.ticketsRepository.findAll().filter((t) => t.travellerId === userId);
    ```
  - Ordinary submitters (`TRAVELLER`, `HOTEL`, `GUIDE`, `EXPERIENCE`) only receive tickets
    where `t.travellerId === userId`.
  - There are no query parameters that allow one submitter to retrieve another submitter's tickets.
  - Individual ticket lookup (`GET /tickets/:id`) is not exposed as a public route; details are
    accessed through `findForUser` filtered by user ID. Confirmed by Source.

D. Input Validation & DTO Constraints:
- File: `backend/src/tickets/dto/create-ticket.dto.ts`
  - `subject`: `@IsString()`, `@MinLength(3)`, `@MaxLength(140)`
  - `message`: `@IsString()`, `@MinLength(10)`, `@MaxLength(1200)`
  - `category`: `@IsOptional()`, `@IsString()`, `@MaxLength(80)`
  - `priority`: `@IsOptional()`, `@IsEnum(TicketPriority)` (LOW, MEDIUM, HIGH)
- File: `backend/src/tickets/dto/resolve-ticket.dto.ts`
  - `resolution`: `@IsOptional()`, `@IsString()`, `@MaxLength(800)`
- Global `ValidationPipe` in `backend/src/main.ts` enforces `whitelist: true`, `forbidNonWhitelisted: true`.
  Invalid payloads or extra fields return HTTP 400 Bad Request. Confirmed by Source.

E. Persistence & Lifespan:
- File: `backend/src/tickets/tickets.repository.ts`
  - Tickets are stored in `private readonly tickets: Ticket[] = []`.
  - When a ticket is created via `POST /tickets`, it is appended to `this.tickets`.
  - When resolved via `PATCH /tickets/:id`, `ticket.status = TicketStatus.RESOLVED`,
    `ticket.resolvedAt = new Date()`, `ticket.resolution = data.resolution`, and
    `ticket.resolvedBy = data.resolvedBy`.
  - This data persists in memory across frontend page refreshes.
  - However, because it is an in-memory repository (like all other repos in this application),
    restarting the backend server process resets the array. Confirmed by Source.
