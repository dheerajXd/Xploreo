2. DETAILED CHANGES BY PRIORITY
--------------------------------------------------------------------------------

### Priority 1: Authentication & Signed-Token Verification
Problem in Phase 4A:
The backend trusted raw incoming request headers (`x-user-role`, `x-user-id`). Anyone
could forge `x-user-role: superadmin` to access administrative endpoints.

Fix Implemented:
1. Backend JWT Issuance (`backend/src/auth/auth.service.ts`):
   - In `login()` and `register()`, the server signs a JSON Web Token using `jsonwebtoken`
     containing `{ userId, username, role, region }` signed by `JWT_SECRET` (`xploreo-dev-secret-key-2026` or `process.env.JWT_SECRET`).
   - The token is returned in the response payload `{ user, token, headers: { Authorization: "Bearer <token>" } }`.
2. Backend Guard Verification (`backend/src/common/guards/auth.guard.ts`):
   - `AuthGuard` inspects the `Authorization: Bearer <token>` header (or `x-access-token`).
   - It validates the cryptographic signature against `JWT_SECRET`.
   - Trusted identity (`userId`, `role`, `region`) is extracted directly from verified
     token claims and populated on `request.user`.
   - Any request lacking a valid signed token is rejected with HTTP 401 Unauthorized
     (except routes marked `@Public()`).
   - Unsigned/unverified client headers (`x-user-role`, `x-user-id`) are ignored and never
     trusted as proof of identity.
3. Frontend Integration (`frontend/src/services/session.js`, `frontend/src/pages/Auth/login.jsx`):
   - Upon login, the signed token is stored in `localStorage` under `xploreoToken` and `xploreoUser.token`.
   - `identityHeaders()` attaches `Authorization: Bearer <token>` to all HTTP requests
     dispatched via `api.js` and `request.js`.

### Priority 2: Trip Ownership & Profile Privacy
Problem in Phase 4A:
Any traveler or external actor could call `GET /trips/:id` or `GET /trips/traveller/:travellerId`
to inspect another user's personal travel plans, passenger names, and hotel details. Furthermore,
calling `GET /traveller/:id` or `GET /guide/:id` exposed personal phone numbers, emails, and
guide bank details (IBAN, account numbers) to third parties.

Fix Implemented:
1. Trip Horizontal IDOR Protection (`backend/src/trips/trips.controller.ts`, `trips.service.ts`):
   - `TripsController.findOne` passes `req.user` to `TripsService.findOne(id, actor)`.
   - In `TripsService.findOne`:
     - If `actor.role === Role.TRAVELLER`, checks `trip.travellerId === actor.userId`. Throws 403 Forbidden if not the owner.
     - If `actor.role === Role.GUIDE`, checks `trip.guideId === actor.userId`. Throws 403 Forbidden if not assigned.
     - If `actor.role === Role.NONTECHADMIN`, checks trip destination matches assigned NTA region.
     - If `actor.role === Role.SUPERADMIN`, permits global access.
   - In `TripsService.findByTraveller(travellerId, actor)`:
     - Travelers can only query their own ID (`actor.userId === travellerId`). Throws 403 Forbidden otherwise.
   - In `TripsService.create(dto, actor)`:
     - Forces `travellerId` to `actor.userId` when called by a traveler, preventing spoofed bookings under another traveler's ID.
2. Traveler Profile Privacy (`backend/src/traveller/traveller.controller.ts`, `traveller.service.ts`):
   - `TravellerController.findOne` accepts `req.user`.
   - `TravellerService.findOne`: If the caller is not the traveler themselves (`actor.userId === id`)
     and not an administrator, sensitive contact fields (`email`, `phno`) are redacted from the response.
3. Guide Profile & Banking Privacy (`backend/src/guide/guide.controller.ts`, `guide.service.ts`):
   - `GuideController.findOne` accepts `req.user`.
   - `GuideService.findOne`: If the caller is not the guide themselves and not an administrator,
     sensitive financial and contact fields (`bank_name`, `bank_acc_num_end`, `iban`, `phone`, `email`)
     are redacted from the response.

### Priority 3: Non-Tech Admin (NTA) Regional Isolation
Problem in Phase 4A:
Regional restrictions on NTA operations existed only in frontend UI dropdowns. Any NTA
could read, create, or update packages in Goa, Mumbai, or Delhi by invoking backend endpoints
directly or tampering with query parameters.

Fix Implemented:
1. Server-Side Trusted Region Mapping (`backend/src/auth/auth.repository.ts`):
   - Seed NTA `NTA001` is mapped with `region: 'Jaipur'`.
   - `AuthRepository.findRegionForUser(userId)` provides authoritative server-side region lookup.
   - The verified NTA region is baked into the signed JWT token claims during login.
2. Regional Scoping on Plans (`backend/src/plans/plans.controller.ts`, `plans.service.ts`):
   - `findAll`: When called by an NTA, the backend overrides any user-supplied `destination`
     filter with the NTA's trusted region (`actor.region`). An NTA cannot view foreign region packages.
   - `create`: Validates `dto.destination.toLowerCase() === actor.region.toLowerCase()`. Rejects foreign
     destinations with HTTP 403 Forbidden ("Cannot create package outside your assigned region").
   - `update`: Validates both the existing package's destination and any proposed destination change
     against `actor.region`. Rejects cross-region tampering with HTTP 403 Forbidden.
   - `findOne`: Verifies the requested package belongs to `actor.region`. Throws 403 Forbidden otherwise.
   - SuperAdmin: Global access is strictly preserved (`findAll`, `create`, `update`, `remove` across all regions).
3. Regional Scoping on Trips (`backend/src/trips/trips.service.ts`):
   - `findAll`: When called by an NTA, filters returned trips to only those located in `actor.region`.
   - `create`: Rejects trip creation if the plan belongs to a foreign destination.
   - `update` / `findOne`: Blocks NTA access to trips outside their region with HTTP 403 Forbidden.
